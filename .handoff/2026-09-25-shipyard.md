## Where you run, and what you do

- **You run on a Linux VPS** (Ubuntu), not a Mac:
  - repository: `/home/yabepa/Developer/yahyabedirhan/shipyard`
  - ghbar reference: `/home/yabepa/Developer/open-source/ghbar`

  `~/Developer/...` paths in this repository's docs resolve to the same places.
- **Your job is to implement only:** write the code, the tests and the docs each ticket asks for, and deliver them for review.
- **Building and verifying need macOS.** The app uses SwiftUI `MenuBarExtra`, AppKit, the macOS notification framework, the Keychain and `SMAppService`, none of which exist on Linux. So `swift build`, `swift test`, `make` and running the app can't succeed on the VPS. Don't install toolchains or work around this, and never report a build or a test as passing when it hasn't run on macOS.
- **Verification is done by the user on their Mac.** With each delivery, write down exactly what to verify there:
  - commands to run (`make test`, `make install`);
  - what to click and what they should see;
  - any acceptance criterion that needs a human check.
- **One automated macOS signal exists once #2 lands:** CI runs `swift test` on a GitHub Actions macOS runner. You may push a branch and read its result with `gh run watch` / `gh run view --log-failed` to catch compile errors early. A green CI run is still not the user's verification.
- **Write tests anyway,** alongside the code, against the seams below. Red-green TDD can't run locally, so keep the tests small, deterministic and easy to review, and let CI and the user run them.

## What the builder should know

- **Toolchain on the user's Mac** (where it gets built): Swift 6.3 with Command Line Tools only, no Xcode. So: SwiftPM plus a Makefile that bundles the `.app` (ghbar's Makefile and `Package.swift` show how), no Xcode project. No Developer ID: ad-hoc signing only. Target Swift 6 and macOS 14 APIs, and check API availability in Apple's documentation rather than by compiling.
- **ghbar** (`/home/yabepa/Developer/open-source/ghbar`) is a reference to learn from, not to copy. Worth reading: `TokenProvider.swift` (finding `gh` from an `.app`), `DeviceFlowAuth.swift`, `RefreshGate.swift`, `SeenStore.swift` (keep seen and notified separate), its tests and fixtures. Its comments are in Turkish.
- **Needs the user (#3):** the device flow needs an OAuth App registered under the user's GitHub account, with device flow enabled, and its client ID. Ask for it. The `gh` token path works without it, so the rest of #3 needn't wait.
- **Main test seam (#5 onwards):** drive the app's `Shipyard` orchestrator end to end, with the network stubbed at the URL-loading layer from recorded fixtures, temporary configuration and app-state directories, a recording notifier and an injectable clock. Assert on the menu model and the notifications posted.
- **Versioning:** start at 0.0.1, stay below 0.1.0 until the user calls the public launch.
- **Not in scope:** anything in the spec's Out of Scope. Don't add a CLI or a settings window (ADR 0001).
