# Shipyard 0.0.2: decisions from the design session

On 2026-09-26 the maintainer and Claude Code designed shipyard 0.0.2. The goal was to make shipyard a superset of [cobanov/ghbar](https://github.com/cobanov/ghbar) through configuration, while keeping the maintainer's own setup (what they and their agents open) working. The session ran in worktree `~/.treehouse/shipyard-1e47e3/1/shipyard` (Herdr workspace `shipyard-0-0-2`), branch `build/shipyard-0.0.2`, session `e60059ac`.

- The questions and answers, word for word: `.scratch/2026-09-26-shipyard-0.0.2-grilling-verbatim.md` (ignored by git; this file is the committed record).
- The design draft: `.scratch/low-level-design-0.0.2.md` (it's merged into `docs/low-level-design.md` once agreed).
- Terms: `CONTEXT.md`. Lasting decisions: ADR 0002 (selector syntax) and ADR 0003 (filters decide what a project lists).

The rule of thumb, in the maintainer's words: "have sensible defaults for each configuration and also allow other users to configure their setup, their layout, what they want to see, and what they want to get notified with as flexibly as possible through configuration." The filtering must stay maintainable as filters are added ("I don't want things to go spaghetti"), and nothing should be over-engineered.

## Authors: whose items a project lists

- Each kind (`pull-requests`, `issues`, `workflow-runs`) takes `authors = { show = [...], hide = [...] }`, in `[defaults.*]` and per project. **Both** `show` and `hide` are kept: `show` is optional and defaults to everyone, and `hide` wins. The result is `show` minus `hide`. `hide` alone covers most views; `show` exists for "only these", such as only `@dependabot[bot]`'s PRs.
- **Author groups:** `me`, `others`, `bots`. `me` is the signed-in account, so agents working as the user count as `me`; it's the shorthand for the user's own `@login`. `bots` is a GitHub `Bot` account or a login ending in `[bot]`; GitHub's API reports bot authors as type `Bot`, so this is deterministic. `others` is everyone else. The three together cover every author.
- **A login** is always written with `@` (`@some-login`, `@dependabot[bot]`). A bare word that isn't a group is an error with a suggestion ("unknown author `bots2` (did you mean `bots` or `@bots2`?)").
- **Syntax history** (ADR 0002): `@me`/`@others`/`@bots` was proposed first. The maintainer rejected it because `@` tags people. Next came `#` for groups and `@` for users, then `$` for author groups with `#` for repository groups. The agreed form uses no symbol for groups: the key already says which set a group belongs to. `@` marks a login and `/` marks a repository. The maintainer asked that this be "really nicely documented in our maintainer documentation and also in the skill".
- **`hide-authors` is removed.** `authors` replaces it. An old file's `hide-authors` is read as a `hide` in each kind's defaults, with a warning, so it keeps working. On the introduction the maintainer noted: `me` in `hide` is how a ghbar user mutes their own contributions everywhere (`hide-authors = ["their-login"]` already does this today, for every project).
- **Notification rules** take the same selectors (`authors = ["others"]`). The old strings (`"any"`, `"me"`, `"others"`, `"bots"`) keep working, with a warning.
- **The example of muting a spammer** is just a login (`@some-spammer`); shipyard doesn't detect spam.

## Repositories: which repositories a project watches

- There is **no top-level scope switch** (no `scope = "all" | "selected"`). A project's `repositories` list takes:
  - `owner/name`: one repository;
  - `owner/*`: everything under that user or organization, so new repositories show up without editing the file (the maintainer's example: "Use the projects under yahyabedirhan/*");
  - the **repository groups** named after GitHub's own affiliations: `owned` (repositories owned by the user's personal account), `organizations` (repositories the user reaches through membership of an organization, directly or through its teams; a repository the user created inside an org lands here), `collaborator` (a repository owned by someone else that added the user by name as a collaborator). The three don't nest. Together they are everything the user can reach. The maintainer chose GitHub's three over a two-group `owned`/`contributed` split ("#contributed doesn't sound like a good idea... embrace the natural GitHub tree so that the terminology is familiar"). `me/*` isn't a form; `owned` covers it.
  - `anywhere`: see Review requests.
- **"All repositories"** means whatever the token can reach: with `gh`, or with the OAuth App (where the user may have granted access to all repositories or a few), shipyard only ever sees what it has access to.
- **With no projects configured**, onboarding still asks, so the choice of repositories is always explicit.
- **Archived and forks:** `archived = false` and `forks = true` by default, and both can be changed ("it should be all configurable"), in `[defaults]` and per project. They apply to repositories that groups and wildcards bring in; a repository named as `owner/name` is always included.
- The list behind groups and wildcards is looked up again from time to time, so new repositories appear; a repository named twice appears once.

## Per-kind filters

The maintainer's framing: "a hierarchical system": the top-level categories (pull requests, issues, workflow runs) can each be shown or not, and each has its own filters. Agreed for 0.0.2:

| Kind | Filter | Values |
|---|---|---|
| all three | `authors` | `show` / `hide` selectors |
| pull requests | `states` | `open`, `merged`, `closed` (default all three) |
| pull requests | `drafts` | as today |
| pull requests | `review-requested` | `true`: only PRs waiting on your review |
| issues | `states` | `open`, `closed` |
| workflow runs | `states` | `in-progress`, `failed`, `succeeded` |

- `closed-window-days` and `finished-window-hours` stay: `states` picks which, the window says for how long.
- `review-requested` is a boolean, not a general "involvement" list; `assigned` and `mentioned` can come later.
- **Filters decide what exists** (ADR 0003): an item a project's filters leave out is not listed, not counted (header, tabs, menu bar) and not notified. A notification rule's `authors` only narrows further. Filters apply identically in both layouts, the All tab included.

## Review requests

- **Team requests count, everywhere**: a request to the user or to a team they're in counts for the `review-requested` filter, `anywhere`, attention and notifications. GitHub's search has both forms, `user-review-requested:@me` and `review-requested:@me`; today shipyard only counts direct requests.
- **`anywhere`** is a repository group for PRs anywhere on GitHub waiting on the user's review. It's there for a public repository whose writers asked the user for a review, where the user is not a collaborator. That PR's repository is in none of the other groups. It's valid only with `pull-requests = { review-requested = true }`, and such a project shows no issues or runs; the app refuses anything else with a clear error. Other filters apply as usual. It's answered by a GitHub search, the one exception to fetching broadly and filtering locally. The maintainer: "a really simple and powerful configuration."
- A review request, in GitHub's sense, only exists on pull requests. Assigning someone needs access, so a random outside assignment isn't a case to cover.

## Arranging a project: grouping, subsections, sorting, folding, Show more

- **Grouping and subsections are two separate choices.** Today a project is already grouped by kind (PRs, then a divider, then issues, then runs) without subheaders. The maintainer likes that view: "It's simple: there are no subsections but they are also grouped by the kind without losing the current simplicity."
  - `group-by = "kind" | "repository" | "date" | "author" | "none"`, in `[defaults]` and per project, one level only. **Default `"kind"`** (today's grouping). The maintainer first said `none` by default, then settled on this split: grouping by kind stays the default and subsections are optional.
  - `subsections = true | false`: groups shown as subheaders (a name and a count) or as dividers (today).
  - `date` buckets: Today, Yesterday, This week, This month, Older, by the `sort-by` date (`updated` when sorting by title).
- **Sorting:** `sort-by = "updated" | "created" | "title"` (default `updated`), direction fixed (newest first, A to Z), open items always before closed. The maintainer: "Think of it like an SQL query": grouped and sorted together.
- **Folding** (collapse and expand, like a project) works on subsections only, since it needs a subheader to click, including ← and → on the keys. The fold is app state and survives restarts.
- **Show more:** `show-first = N` (default `0`, show all) shows a group's first N rows and a "Show N more" row, which becomes "Show less". It works with subsections and with dividers, the keys reach it and Return toggles it. The expansion isn't remembered: it resets when the menu closes. Folding and Show more combine: a folded group shows only its header; an open one shows its first N rows.
- **Both layouts:** the first level is the project (tabs split projects into tabs, the list shows them one under another); the second level is `group-by`, the same in both. The **All tab** is the one fixed view: grouped by kind, newest first, with dividers.
  - Resolved in the build: the All tab groups by kind, newest first, under subheaders, not dividers.
- **Still open:** the tabs layout already shows small kind subheaders today, while the list uses dividers, so a single `subsections = false` default would change the tabs. Proposed: `subsections` defaults to what each layout does today (dividers in the list, subheaders in tabs); a value the user sets applies to both.
  - Resolved in the build: settled as proposed. An unset `subsections` follows the layout (dividers in the list, subheaders in a tab); a value the user sets applies to both.

## Presets and onboarding

- **Three presets**, named in kebab case: `my-agents` (everything you and your agents open in your repositories: the maintainer's setup), `incoming-contributions` (what other people open on your repositories, bots hidden, plus PRs anywhere waiting on your review: ghbar's view), `review-queue` (only PRs, anywhere, waiting on your review).
- **Presets are defined in the app itself** and also listed in the skill, so users' agents can refer to them; a test keeps them equal. Claude decides their exact contents (proposed in the design draft).
- **Onboarding lets the user pick a preset.** The maintainer: "it'll be easy to implement and will improve the user experience and let the presets be more visible and more meaningful." Claude decides the flow. Proposed: pick a preset first. `my-agents` then shows today's repository picker, `incoming-contributions` offers "all my repositories (`owned`)" or picking, and `review-queue` needs no repositories. Writing the preset is a third targeted edit to the file (ADR 0001 gets amended).

## Out of scope for 0.0.2, possible later

- Deployments waiting for the user's approval (a later workflow-runs filter; the maintainer asked that this be noted as out of scope and possibly included later).
- Folding busy projects automatically, as ghbar folds repositories with more than three items ("Maybe we can add it later on if other users request it").
- The picker offering groups other than the presets' `owned`.
- `assigned` and `mentioned` filters, oldest-first sorting, nested grouping.

## What ghbar gives, and where 0.0.2 covers it

| ghbar | 0.0.2 |
|---|---|
| PRs and issues others opened on your repositories | `authors = { hide = ["me", "bots"] }` with `owned` (the `incoming-contributions` preset) |
| Every repository you own, no setup | `owned` / `owner/*` |
| PRs anywhere waiting on your review | `anywhere` with `review-requested = true` |
| Bots hidden by default | `hide = ["bots"]` (shipyard's defaults stay as today; presets do it) |
| New vs seen, count in the menu bar | already there |
| Busy repositories folded | not in 0.0.2 (UI only, later) |
| Honest about failures, low API cost, refresh on wake and ⌘R | already there |
| Sign-in without `gh` | the merged-in sign-in work |
